01 · Why

AI agents write code fast. They also skip the boring, important parts.

Skipped by default
  • Specs
  • Tests
  • Security reviews
  • Everything else that makes software reliable
What a skill adds

A step-by-step recipe the agent must follow, with a clear "done" check at the end. Like a Definition of Done, but for your AI.

03 · What is a skill?

A skill is a recipe file the agent reads and follows

skills/test-driven-development/SKILL.md
name + description
Tells the agent when to use it
Overview
What this skill does
When to Use
The trigger conditions
Process
The steps, in order
Rationalizations
Common excuses and why they're wrong
Red Flags
Signs something is going wrong
Verification
Proof required before calling it done

It's a plain Markdown file. No SDK, no framework.

Think of it as a runbook written for the agent instead of for a person.

Every skill has the same shape, so the agent always knows where to look.

06 · The clever part

Agents make excuses. Skills answer them in advance.

The agent thinksThe skill answers
"I'll add tests later."Tests are the proof. No test, not done.
"It seems right."Not enough. Show passing tests, build output or runtime data.
"It's a small change, skip the spec."Spec before code. A short spec is still a spec.

Every skill ships a table of these excuses with a counter-argument, and ends with the evidence it needs before it may say "done". In this repo, that evidence rule caught a real bug: removing @Transactional left all 38 unit tests green while stock stopped being saved. The integration test was added to prove it.

07 · Where the ideas come from

Battle-tested ideas, in plain words

Hyrum's Law

If users can see a behaviour, someone depends on it.

→ API design

Beyoncé Rule

If it matters, put a test on it.

→ Testing

Test pyramid 80/15/5

Mostly unit tests, some integration, few end-to-end.

→ Testing

~100-line changes

Small changes get real reviews.

→ Code review

Chesterton's Fence

Know why code exists before you delete it.

→ Simplification

Trunk-based development

Short branches, merge often.

→ Git workflow

Shift Left

Catch problems as early as possible.

→ CI/CD

Feature flags

Ship code switched off, turn it on safely.

→ CI/CD · Launch

Code is a liability

Less code to keep alive is better.

→ Deprecation

Sources: Software Engineering at Google and Google's engineering practices guide.

Use the full lifecycle from day one.
